# NeoOrg 参赛演示视频方案

视频以一个产品负责人的真实工作方式为主线：面对不完整的试点数据，和有明确岗位的 AI 同事共同形成可追踪、经过独立评审的决策建议。评委应能记住三个区别：每个目标有持续负责的人，贡献按需发生，交付还要经过独立评审。人类提供约束并保留最终业务决定权。

本轮交付策划方案，尚未录制或生成成片。PPT、发布视频、填写表单和最终比赛提交不在本轮范围。

## 比赛要求与制作规格

按当前提交页截图的 3–4 分钟要求，主版按 3:00 编排，包括片头片尾。公开赛道页写 3 分钟，旧 FAQ 和当前公开 Terms 仍写严格不足 3 分钟，文字存在冲突；3:00 不能被称作同时满足全部公开文本。同一时间线保留一版 2:55 的裁剪备份，供提交字段实际限制需要时选用，不以旧 FAQ 自动推翻用户提供的后台要求。[赛道与提交要求](https://aibuildercup.com/themes.html)、[FAQ](https://aibuildercup.com/Faqs.html)、[公开 Terms](https://docs.google.com/document/d/e/2PACX-1vRm7ChZ6Ij9fG7uFDkxzUMpwgVeBmnQ6cMDnAIEEX84AiLBOOQ9cYbl3S5OzFBbcVb8TF55s-eVpiXb/pub)

材料采用英文：英文产品交互、英文旁白和英文字幕。拟输出 1920×1080、16:9、30fps 的 H.264/AAC MP4，另附 SRT 字幕和封面；画幅、编码、帧率是本方案的制作选择，不是宣称官方另有硬性格式规定。官网允许以公开 YouTube、Vimeo 或 Google Drive 视频链接提交；制作完成不等于获得上传或发布授权。[提交要求](https://aibuildercup.com/themes.html)

官网当前列出的原型截止日为 10 月 18 日，精确截止时刻和时区以后台为准。优先在 10 月 17 日形成可审阅成片，避免把首次出片压到截止日。[比赛时间线](https://aibuildercup.com/)

## 演示场景

身份是准备扩大 onboarding 试点的产品负责人。场景明确标为 `Synthetic demo case`，沿用当前产品推荐问题中的五团队样例：同一版本由五个团队测试，四个独立完成，一个需要操作员协助，尚未做重复恢复测试。这些是演示输入，不是客户数据或产品实测业绩。

新建 `Pilot launch decision` 群聊并选择四位 Agent。简短展示 Harbor 的协调岗位、Reef 的研究与证据岗位、Sail 的规划岗位和 Beacon 的质量与风险岗位。岗位是长期身份，本次谁负责目标、谁贡献、谁评审以真实运行结果为准，不预先伪造分工。

建议的首条任务如下，正式文案在彩排后定稿：

> @Harbor We need to decide whether to expand our onboarding pilot tomorrow. Synthetic demo case: five teams tested the same build; four completed onboarding independently and one needed operator help. We have not repeated recovery tests. Before your final recommendation, ask me how much support we can allocate; do not assume it. Use only the supplied facts, request useful teammate contributions, and deliver a GO / LIMITED GO / HOLD recommendation with evidence gaps, a three-step plan, responsible roles and exit criteria. Do not claim that any tests or rollout actions have been executed.

预期的关键协作片段是负责人提出支持资源问题，系统显示等待人类输入，再由用户回答：`We can support only two teams next week. Keep the pilot limited and require a repeat recovery check before expansion.` 随后负责人保持同一目标的责任，整合专业贡献并提交交付，再由独立成员按验收条件评审。

这个等待与继续必须在真实彩排中出现。若模型没有产生 input gate，不把普通新聊天剪成“同一目标恢复”，也不修改 Firestore 或响应文本来配合脚本。先调整明确的业务任务表述并重新完整录制；若仍不稳定，主片保留已验证的真实协作主线，将输入门从必拍镜头降为候选，不为拍片临时改产品。

## 三分钟分镜

| 时间 | 画面与叙事 | 观众需要看懂的事实 |
|---|---|---|
| 0:00–0:15 | 以负责人视角提出试点决策困境，快速出现 NeoOrg 当前产品界面 | 一份答案还不够，工作需要明确责任和可检查的结果 |
| 0:15–0:35 | 加号建群、选成员，打开一个岗位侧栏；其余岗位用简短标注介绍 | 这是可选择、有职责与能力边界的同事，不是同一个聊天机器人的四个名字 |
| 0:35–0:55 | @ 提交带事实与验收要求的任务，突出真实 owner 标记 | 用户给目标和约束，系统形成一个持续负责的目标 |
| 0:55–1:55 | 专业贡献、真实人类输入门与补充资源、负责人整合交付；围绕同一任务剪辑 | 事实缺口、资源限制、方案与退出条件进入同一交付，人物与目标不漂移 |
| 1:55–2:20 | 展示独立评审、展开验收条件，停留读清楚最终建议与关键行动；刷新返回 | 交付与评审不同；结果可检查，刷新后仍在，而不是临时聊天动画 |
| 2:20–2:45 | 简洁技术示意配真实发布/调用证据局部：浏览器、Cloud Run、Gemini on Vertex AI、Firestore | 模型做语义判断，工程维护状态与持久化；浏览器没有模型凭证 |
| 2:45–3:00 | 回到完整结果，NeoOrg 名称、Future of Work 赛道、应用和 GitHub 入口 | 从目标到有负责人、经过评审的交付；最终业务决定仍由人作出 |

旁白先按约 330–360 个英文词试读，再用实际语音时长调整。录屏允许剪掉等待或注明加速，但不把剪辑后的秒数宣传为完整任务耗时。关键建议和评审要有足够停留时间，不能只展示滚动的长消息。2:55 备份主要缩短开头与结尾，不删除独立评审或技术证据。

## 录制与剪辑方式

1. **先定台词和样片。** 输出英文逐镜头脚本、中文审阅释义和 15–20 秒风格样片，确认叙述是否清楚、字幕能否读清、音色是否合适。默认不要求用户出镜或录音。
2. **再跑真实场景。** 使用独立、只含演示数据的浏览器会话与新群聊，在当前已部署 Cloud Run 产品调用真实 Gemini，核对同一目标的 owner、贡献、交付、评审和刷新持久化。只使用提供的材料，不暗示 Reef 做了未接入的联网检索。
3. **录完整母带。** 从建群到结果保留连续原始录制及对应运行记录，剪辑选择来自同一次业务链。若真实请求失败，保留证据，按系统正式恢复动作处理；不拼接不同运行来伪造连续成功。
4. **合成可编辑时间线。** 拟用 Remotion 管理录屏片段、放大取景、字幕、章节标注和简短技术示意。产品画面沿用 NeoOrg 当前 Logo 与蓝灰视觉；动画只解释已有画面，不代替尚未实现的功能。[Remotion 录制和剪辑文档](https://www.remotion.dev/docs/recorder/)、[渲染接口](https://www.remotion.dev/docs/renderer/render-media)
5. **完成两轮验收。** 先审阅叙事和事实，再审阅正式输出的清晰度、字幕、音量、精确片长和可播放性。最后交付主版、时长备份、字幕、封面和可编辑工程。上传平台后的公开访问检查另行进行，不能在上传前宣称已通过。

视频工程与产品依赖、部署链路隔离。当前机器有 Node/pnpm 和系统英文语音，尚未配置 Remotion 与 FFmpeg 工具；制作开始先验证录制、编码和音轨的小样，再批量制作。英语合成旁白先试听，不克隆真人声音，不默认购买 TTS 或音乐。若系统音色不适合作成片，再选择有明确授权的配音来源；付费方案另行确认。第一版可不加音乐，保证旁白与产品信息优先。

## 事实与画面验收

- 画面来自当前已部署 NeoOrg；录制前重新核对发布版本。真实 Gemini 调用以对应任务的调用记录和交付为依据，健康端点只能证明配置与存储探测，不能单独证明推理成功。
- 负责人始终可识别；贡献者不关闭目标，评审者不参与该交付的创作。实际角色与屏幕标注一致。
- 人类补充输入必须消费真实等待中的目标；负责人和旧消息保留。已完成目标后的新消息不能被包装成自动恢复旧目标。
- 最终建议可读，有事实缺口、行动与验收条件；`Reviewed · Goal achieved` 不能旁白成“试点已成功上线”。本原型交付文本，不执行上线、测试、发邮件或外部系统写入。
- 不声称接入 Firebase Hosting/Authentication、独立 Worker/PostgreSQL、长期记忆或完整 NeoOrg 平台。Firestore、Cloud Run 和 Vertex AI 的作用与现有实现一致。
- 不露出 room token、访问凭证、私人浏览器标签或无关项目数据。技术证明使用脱敏的发布/调用片段，不录制环境变量和密钥页面。
- 英文字幕不遮住输入区和验收结果；缩到 1280×720 仍能读到核心信息。逐镜头检查片首、片尾、转场与音画同步，全片正常速度试听。
- 合成场景数据与正式模型输出来源可区分；不伪造客户、节省时间、多 Agent 优势或基准成绩。原片中的等待如被压缩，画面注明。

先确认本方案的核心场景，再完成英文脚本与 15–20 秒样片；样片审阅后录制真实任务并剪出完整粗剪，最后修订为正式主片与 2:55 备份。短窗口内优先保证真实任务和清晰旁白，再完善字幕与局部动效，不扩展新产品功能，不依赖伙伴的 PPT 完成才能拍摄。
